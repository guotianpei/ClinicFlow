# M02 CP0 — test-driven execution-route reconciliation v2

## Finding and proposed correction

The existing M01 handle dispatches catalogued statements on the gateway connection; it does not execute Python under the owner of a preceding definer function. The pure Python engine therefore cannot directly invoke the owner-only finalizer merely because an append function ran first. Likewise t001 supplies the tenant audit-outbox table but the production statement catalogue contains no audit append callable. Both are missing routes, not evidence of failed runtime deployment: M02 is not implemented.

Propose two narrow completion wrappers, not public EventFoundation methods:

| Route | Proposed signature | Owner / external caller | Internal call |
|---|---|---|---|
| append completion | m02_complete_append(p_operation_id uuid, p_result jsonb, p_handoffs jsonb) returns jsonb | append owner / haloflow_runtime via registered WRITE statement | m02_finalize_operation |
| correction completion | m02_complete_correction(p_operation_id uuid, p_result jsonb, p_handoffs jsonb) returns jsonb | correction owner / haloflow_correction via registered WRITE statement | m02_finalize_operation |

These extend the proposed SQL inventory and require review; they do not broaden direct finalizer ACLs. No PUBLIC EXECUTE; no generic function selector; separate M01 capability per route. Null-operation paths do not invoke either operation finalizer. Exact wire schemas must reject unknown fields, unrelated evidence, unsupported engine/rule codes and unbounded commands. The handoff list is service-derived under the reviewed snapshot: local validation proves structure and scope, not that the list is complete. That remains A's accepted service-correctness residual.

Proposed statement keys/capabilities: m02.append.complete and m02.correction.complete, mode WRITE. A service context must hold both its entry-specific append/correction capability and the appropriate completion capability; the two checks are distinct. These are proposed names, not registrations. A capable malicious or erroneous service may call a wrapper outside the intended sequence; no transaction marker or cryptographic attestation is invented. Wrapper validates current operation/evidence and finalizer repeats complete-set comparison. This does not establish proof of preceding append or required-handoff completeness.

## Complete-evidence route

Public tier views deliberately omit raw metadata, internal fingerprints and other engine inputs. Do not use those views as a complete fold source and do not widen their fields silently.

Propose internal m02_load_operation_evidence(p_operation_id uuid) returning a closed, versioned envelope of immutable events, links and canonical binding required by the engine, owned by read owner with no writes. Exact columns come from the later compiled engine-input manifest. Proposed registered READ key/capability m02.operation.evidence.read. Runtime, correction and projection worker caller roles need this EXECUTE for their approved service paths; capability and subject/operation entitlement are validated before dispatch by M01/service. This is elevated internal evidence access, never a public API result. No events from another operation or tenant, no key-control reads, no arbitrary query or metadata logging. Read-owner effective access and caller rights must be reviewed explicitly; this is not already authorized by structural-view capability.

Write orchestration: acquire the existing operation lock; append immutable evidence through the purpose-specific gateway; load full evidence; run pure engine; append generated conflict evidence through the owning gateway if required; reload/refold; call the matching completion wrapper; commit; only then expose success. New-operation handling inserts identity before locking its row. The service does not acquire a new connection or nested tenant transaction. Multi-operation work follows ascending UUID byte order. Full-history work remains O(n), with unmeasured bounds; no pagination that silently drops older evidence.

Read fallback: propose compute-only under the existing read transaction and explicit unavailable when the complete reviewed input cannot be obtained. No public tier call automatically gains the elevated evidence capability. A caller lacking it gets the approved explicit-unavailable behavior when cache cannot satisfy consistency. Exact consistency-mode names and freshness thresholds remain to be specified. This is a capability consequence to review, not silent support for all recompute requests.

## Atomic audit and null-operation durable work

Propose correction gateway itself inserts the structural audit record into existing tenant access_audit_outbox in the same transaction, using an explicit column-scoped INSERT grant to correction owner. No new shared writer and no new audit table. This is a new proposed local grant replacing the unsupported assertion of an existing callable, and requires independent architecture review and final owner alignment.

Proposed audit insert columns from existing t001: source_event_id, action_code, resource_class, purpose_code, outcome_code, principal_kind, principal_id, execution_id, request_id. Leave occurred_at to its database default and projected_at untouched. Principal_kind must satisfy the existing actor/workload constraint. Source_event_id binds the correction/resolution evidence; controlled action/purpose/outcome vocabulary and trusted M01 principal/execution/request mapping must be enumerated before this grant can be called complete. No raw metadata/reason text in audit fields. Duplicate retries must validate equivalence and preserve the original audit identity, not overwrite or silently ignore conflicting content. Null-operation correction follows the same route without an operation projection.

For null-operation observation/correction contract-required structural handoffs, propose private m02_enqueue_event_handoffs(p_event_id uuid, p_handoffs jsonb), projection owner, callable only by append/correction owners from their narrow gateways. It validates local source identity, allowed kind, closed payload and deterministic key, inserts outbox only and never fabricates an operation projection. It receives no public runtime EXECUTE. This fills the non-operation outbox route missing from the operation-only finalizer. Again, required-list completeness is service/contract correctness under A.

## Named test obligations added to TC01–23

- TC24 completion ACL: public/direct finalizer call denied; append wrapper succeeds only for its permitted caller and capability; correction wrapper independently tested; no owner membership. Assert actual call chain and complete source comparison. Wrong role and malformed command are separate negatives with valid controls.
- TC25 omission/call ordering: omit wrapper, omit handoff, add fact after fold, or return before gateway completes; service-oracle test detects each. Stale result rejected by finalizer when called. No assertion that an omitted call prevents database commit.
- TC26 evidence access: each allowed internal role/capability positive; tier-only context denied internal evidence; wrong tenant/operation denied; exact internal envelope and no key-control data. Public serialization never includes internal-only sentinels.
- TC27 audit atomicity: correction/resolution and audit insert succeed together; audit failure rolls back new evidence/projection/work; projected_at cannot be supplied or updated. Retry equivalence and conflicting audit identity tested independently; null-operation correction included.
- TC28 null-operation outbox: observation and correction with a synthetic allowed durable-work rule invoke the private event route; no projection row; wrong source and arbitrary kind rejected; omission regression fails the service oracle.
- TC29 read fallback: cache satisfies policy without elevated read; stale/missing cache plus authorized evidence capability computes without persistence; lacking capability yields explicit unavailable; no capability escalation, new handoff or provider call.

Handoff key oracle from design §10.1: M05 uses tenant+operation+kind, M06 tenant+operation, M11 tenant+source-event+signal-type. Pin encoding/version separately; source event must not accidentally split a single M05/M06 logical key. Null-operation M05/M06 needs a reviewed contract-specific alternative and is not invented here; null-operation event_signal uses the source-event key. Test fixtures should use this supported event_signal path until another rule is approved.

They are within CP0 design drafting but are not automatically accepted schema/grant decisions. No existing approved grant is silently overwritten. ## V2 — Claude227 conditions and threat-specific cases

Claude227 read in full. Necessity endorsed; authority approval remains conditional, not final schema or owner alignment approval.

Minimum-necessary evidence (FR-020, design §13.4): complete means every reviewed input needed by the selected engine, not every stored column or entire metadata object. The compiled engine-input manifest must enumerate each field/path, type, purpose, contract version and permitted internal consumer. Unknown/unlisted fields and nested metadata paths are omitted or fail closed as the contract specifies; no SELECT *, whole-row JSON or unrestricted metadata copy. SQL envelope construction and service validation must enforce that same manifest. Every returned field requires a documented engine need and authorized internal consumer, independently of public tier access. The exact manifest remains physical-contract work; this principle applies now. Internal envelopes must never become public responses, logs, exception bodies or telemetry. Public results are constructed separately from their reviewed field allowlists, not by forwarding the internal envelope.

TC26 additions: enumerate actual manifest fields and metadata paths using synthetic values, including sensitive-class fields; verify each input has its declared engine purpose and consumer authority. Inject an unlisted top-level field, nested metadata property and prohibited raw payload separately; confirm no returned envelope contains them. Verify exact allowed values still reach the pure engine. Exercise each public result/error/log serialization and confirm internal-only fields/paths are absent, rather than relying only on one sentinel string. No real PHI is needed. A synthetic sentinel detects leakage, but manifest/path assertions establish the field-boundary coverage.

Audit-forgery threat: a caller-supplied principal_id could falsely attribute a correction to someone else. Public correction commands therefore must not choose audit principal_kind/principal_id, execution_id or trusted request provenance. The trusted service derives them from the validated M01 context and approved execution context, and compares any evidence attribution to that identity before SQL dispatch. Exact attribute names and controlled-code mapping still require enumeration; mutable session settings and current_user inside a definer are not independent principal authentication.

TC27 additions: with a valid authorized actor A, inject actor B, a workload identity, another execution identity and an untrusted request attribution one at a time; each public/service attempt is rejected before audit/event mutation, with a valid A control. Cover both correction and resolution and null-operation correction. Direct runtime audit INSERT authority must be characterized separately: t001 default runtime DML exists, and this proposal has not removed it. Likewise a malicious trusted service or correction owner with INSERT may forge attribution under the existing application-trust boundary. Do not claim SQL independently prevents that. If prevention against those actors is required, it needs a separately reviewed mechanism; no new residual acceptance is inferred. This distinction is essential to reviewing the mapping rather than claiming an unenforced anti-forgery guarantee.

Alternatives: runtime direct finalizer EXECUTE was not selected because it bypasses the intended owner-mediated entry and widens direct caller authority. Moving the fold into SQL would change the design §9.1 pure engine implementation shared with rebuild and require separate equivalence/design review; FR-014 requires determinism but does not itself mandate Python. The wrapper preserves the chosen architecture while making the round trip explicit.
